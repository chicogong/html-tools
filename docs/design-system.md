# WebUtils 界面维护标准

WebUtils 已有明确的暗色科技感、青色强调色与亮色主题。这套现有识别是产品资产；日常维护应保留首页封面、视觉基调和用户已经熟悉的交互，除非产品负责人明确批准重新设计。

## 维护原则

1. **先保真，再修复**：维护性修改不顺带换肤、重排首页或重写品牌表达。
2. **任务清晰**：用户应快速找到输入、主要操作、结果与错误恢复方式。
3. **边界准确**：本地处理、外部依赖和网络请求必须如实说明，不能统一承诺“完全离线”。
4. **共享层优先**：通用颜色、字体、间距、控件和工具页外壳由 `assets/css/tool-base.css` 管理；工具内联样式只处理任务特有布局。
5. **渐进改良**：无障碍、兼容性和响应式修复应尽量不改变既有视觉，并通过代表性页面回归。

## 现有视觉约定

- **主题**：默认暗色、可切换亮色；保留现有背景层级、青色强调色和分类色。
- **字体**：Space Grotesk 用于界面与正文；JetBrains Mono 用于代码、输入、数据和短标签。
- **层级**：优先沿用现有 token、边框、阴影和圆角，不在单个工具里创建第二套全局主题。
- **动效**：只动画必要属性，避免 `transition: all`，并支持 `prefers-reduced-motion`。
- **变更边界**：首页封面、品牌色或跨站布局调整属于产品设计变更，不归入例行维护。

## 工具页基线

每个工具至少满足：

- 一个语义明确的 `<h1>` 和一个主要内容区域；
- 表单控件有可点击的 `<label>`，并配置合适的 `name`、`type`、`inputmode` 与 `autocomplete`；
- 图标按钮有具体 `aria-label`，动态结果按需使用 `aria-live="polite"`；
- 所有主要操作可用键盘完成，`:focus-visible` 清晰可见；
- 移动端触控目标适当，不禁止页面缩放；
- 错误与空状态说明发生了什么以及下一步怎么做；
- 外部 CDN/API 无法离线时，在工具页明确说明。

## 新工具结构

新工具应引用共享基座，并从同分类中已通过验收的工具复制结构：

```html
<link rel="stylesheet" href="../../assets/css/tool-base.css" />

<main id="main-content">
  <header>
    <h1>工具名称</h1>
    <p>说明用户能完成什么，以及数据是否离开浏览器。</p>
  </header>
  <section aria-labelledby="input-heading">
    <!-- 工具自己的输入、操作和结果 -->
  </section>
</main>

<script src="../../assets/js/tool-chrome.js"></script>
```

## 验收

界面维护至少检查首页与代表性工具页的桌面/移动、明/暗主题，并运行：

```bash
npm run build
npm test
npm run lint
npm run format:check
```

批量维护优先修改共享层；确需迁移存量页面时，按分类分批，保留可审查差异并安排独立验收。
